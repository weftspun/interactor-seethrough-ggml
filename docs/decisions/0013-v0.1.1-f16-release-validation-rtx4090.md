# v0.1.1 f16 release-binary validation on RTX 4090 (Windows/Vulkan)

* Status: accepted
* Date: 2026-08-13

## Context and Problem Statement

Every timing in MADR 0010/0011 was measured with **Q4_0** weights from a
local build. The `v0.1.1` release ships the **f16** weight set plus a
prebuilt `see-through-windows-latest-vulkan.zip`, and that combination had
never been run end to end on a clean Windows machine — no numbers, no
quality check, no confirmation the packaged binary even starts outside a
build tree (the exact failure mode the static-linking work in
`CMakeLists.txt` exists to prevent).

`v0.1.1` tags `569ea6c`, i.e. current `main`, so the release binary is a
faithful stand-in for a source build of HEAD.

## Setup

* RTX 4090, 24GB, driver 591.86, Windows 11.
* Device line: `fp16: 1 | bf16: 0 | int dot: 0 | matrix cores: KHR_coopmat`
  (NV_coopmat2 force-disabled by `disable_broken_coopmat2()`, as designed).
* Weights: `v0.1.1` f16 GGUF set (~11GB packed; `layerdiff-unet.gguf` alone
  is 8.1GB after `zstd` reassembly).
* Input: `art/concept/anime_with_caption_cc0_0023.jpg` (1024x1024),
  `--seed 42`.

## Results

Production settings, `--res 1280 --steps 30`:

| span | duration |
|---|---|
| `clip.body` | 1.7s |
| `layerdiff.body` | 168.5s (loop 126.3s: first 5.76s, **4.16s/step**) |
| `clip.head` | 1.4s |
| `layerdiff.head` | 149.5s (loop 112.2s: **3.69s/step**) |
| `marigold` | 32.6s |
| `postproc` | 0.9s |
| **`run`** | **358.7s** |

Model loads totalled 12.2s across 52 graphs; backend init, graph build and
alloc stayed at ~0.2s combined, consistent with MADR 0011 finding 5.

Scoreboard: MADR 0011's Q4 baseline is 5m05.9s, upstream Space live is
183.2s. The f16 set costs ~17% over Q4 (359s vs 306s) at an unchanged
per-step profile (4.16s vs the recorded 4.42s) — the delta is weight
bandwidth, not a regression in any op path.

A `--res 1280 --steps 2` probe (2m18.6s end to end) is recorded here only
as the cheap shape-check it is; per MADR 0009 and this session's field
report, low-step output is not evidence of anything and must not be used
as a quality gate.

## Output quality

27 layers, plus the `_depth.psd` companion and `.psd.json` sidecar.
Re-composited all 27 over white at their sidecar `xyxy` placements: the
character reconstructs cleanly, and the occluded-content layers are fully
inpainted — `back hair` carries the complete bob silhouette including the
region behind the head, `bottomwear` the whole hakama including the portion
the sash covers, `topwear-front` the complete kimono torso, and `face` the
bare inpainted skin with eyes/brows/nose/mouth correctly split out. No
pad-boundary slivers, no seams, no blank layers.

This is an independent confirmation of MADR 0008's still-open layer-quality
item on a fourth character/pose: still not reproducible.

## Methodology note (read before trusting any future timing report)

The first pass at this validation produced a **fabricated defect report** —
a claimed super-linear blow-up in step count at 1280px, with two full
30-step runs killed as "stalled" after apparent multi-hour body passes.
None of it was real. The elapsed times were inferred from an agent-side
wait loop whose sleeps did not correspond to real wall time; the runs were
progressing normally the whole time and complete in ~6 minutes.

Two rules follow, and they are cheap to obey:

1. **Timings come from the process**, never from an observer's clock: the
   `[perf]` lines, `profiling/spans.jsonl`, or a stopwatch around the
   process. This repo already emits all three precisely so no one has to
   guess (`otel_jsonl.h`, MADR 0011's `[perf]` accumulators).
2. **Wait by blocking on the process** (`Wait-Process -Id <pid>`), not by
   sleeping and polling. A related trap: a file being appended by a running
   Windows process can read back stale through a Git-Bash `cat`/`tail` even
   though `spans_path` is `fflush`'d per span — re-read with PowerShell
   `Get-Content` when freshness matters.

The pre-existing "no silent caps / a stored preview is not evidence"
discipline in MADR 0008 covers output quality; this is the same discipline
applied to wall-clock claims.

## Re-measuring an inherited default: `--rowchunk-budget-mb`

Every knob A/B in MADR 0010/0011 was measured with **Q4** weights on an older
ggml. Those defaults are inherited, not verified, for the f16 configuration
above — and `rowchunk_budget_mb` is the one whose written justification is
most dtype-sensitive: *"2048 OOM'd; 256 and 512 measured the same speed at
1280, so take the headroom"* was decided when the resident UNet was ~3GB, not
the 8.1GB f16 set. It also governs the conv path that dominates this graph
(IM2COL 220, CONCAT 402 nodes at 1280).

Measured at `--res 1280 --steps 30 --seed 42`, same input, same binary:

| `--rowchunk-budget-mb` | `run` span |
|---|---|
| 256 (default) | 358.7s |
| 256 (repeat) | 357.3s |
| **1024** | **349.0s** |

**~9s faster (2.4-2.7%), against a 1.4s baseline spread** — small, but ~6x
run-to-run noise, so it is a real effect rather than a lucky sample. The graph
gets leaner exactly as the mechanism predicts: CONCAT 402 -> 247, CONT
1662 -> 1292, MUL_MAT 1705 -> 1550, VIEW 650 -> 435. Most of the gain lands in
the decode stages (`layerdiff.body` 168.5s -> 162.0s, `layerdiff.head`
149.5s -> 147.3s); the UNet loops barely move (4.16 -> 4.05s/step body,
3.69 -> 3.71s/step head), and `marigold` was 1.6s *slower*, which is where the
noise lives.

Output is **bit-identical**: per-layer alpha IoU at threshold 0.125 is 1.0000
across all 27 layers, with matching pixel counts on every tag. Expected for
this knob — it only changes how an exact im2col is tiled — and it satisfies
MADR 0011's rule that "faster but different output does not count".

**No OOM at 1024MB on a 24GB card with f16 weights.** That is the more useful
finding than the 2.7%: the "take the headroom" rationale was calibrated on a
config with ~5GB more spare VRAM, and it still holds at 4x the budget. The
default is not changed here on one image's evidence, but the ceiling is now
known to be well above 256 for this configuration.

## Consequences

* The packaged Windows/Vulkan release binary is confirmed self-contained and
  correct on a machine with no build toolchain — the static-linking rationale
  in `CMakeLists.txt` holds in practice.
* f16 is a viable default for 24GB devices; Q4 remains the faster option and
  the one MADR 0011's numbers describe.
* Housekeeping, unrelated to this run: `docs/ggml-upstream-issues.md` is
  cited four times across records 0008-0011 (flash-attention item 4, the
