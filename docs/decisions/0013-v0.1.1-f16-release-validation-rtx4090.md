# f16 release weights are a supported configuration on 24GB devices

* Status: accepted
* Date: 2026-08-13

## Context and Problem Statement

Every timing and quality gate on record (MADR 0009, 0010, 0011) was produced
with **Q4_0** weights from a local build. The `v0.1.1` release ships the
**f16** weight set together with prebuilt platform binaries, and that
combination had never been run end to end — so the packaged artifact was
unproven on a machine without a build toolchain, and the f16 path had no
numbers, no quality check, and no statement about whether it fits a 24GB card
at production settings.

## Decision Outcome

**f16 is supported at 1280px/30 steps on a 24GB device**, and the packaged
release binary is confirmed self-contained: an unmodified
`see-through-windows-latest-vulkan.zip` completed a full production run on a
host with no toolchain, in **358.7 s**, producing 27 correctly cropped,
fully-inpainted layers with no seams or blank layers. Peak VRAM ~16.6 GB with
no host-memory spill.

Q4 remains the faster option and the one MADR 0011's numbers describe; f16
costs roughly 17% more end to end at an unchanged per-step profile, consistent
with weight bandwidth rather than any regression in an op path. That figure is
an estimate across sessions and ggml versions, not a controlled A/B.

Evidence, apparatus, the per-stage spans and the hypotheses behind them are in
the logbook entry
[2026-08-13-4090-f16-release-validation](../logbook/2026-08-13-4090-f16-release-validation.md),
including a refuted hypothesis worth reading: an apparent super-linear
blow-up in step count that turned out to be a measurement artifact, and the
two rules adopted so wall-clock claims cannot be fabricated that way again.

### Inherited knob defaults were spot-checked, not re-derived

Because every prior knob A/B used Q4 on an older ggml, those defaults are
inherited rather than verified for f16. `rowchunk_budget_mb` — the most
dtype-sensitive of them, since its rationale turns on VRAM headroom — was
re-measured: 1024 MB is ~9 s faster than the 256 MB default (2.4-2.7%, about
6x run-to-run noise) with **bit-identical output** (per-layer alpha IoU 1.0000
across all 27 layers), and no OOM at 4x the default budget.

**The default is unchanged.** A sub-3% gain measured on one image on one host
does not justify moving a value whose comment records a real OOM ceiling. What
this establishes is that the ceiling sits well above 256 MB for this
configuration, so the knob is available as headroom rather than a constraint.

## Consequences

* The static-linking work (PRs #1, #2, #5) is confirmed effective in practice,
  not just in CI.
* Users on 24GB cards can take the f16 release without converting weights,
  accepting ~17% over Q4.
* The remaining inherited defaults (`decode_batch`, `linear_fast_body`,
  `conv_f16`, `tiled_attn_layerdiff`) are still unverified under f16. Each has
  a recorded Q4 A/B; none has been re-run. They are not known to be wrong, only
  unconfirmed for this weight set.
* Housekeeping, unrelated: `docs/ggml-upstream-issues.md` is cited four times
  across records 0008-0011 but does not exist in the tree. Either restore it or
  drop the references.
